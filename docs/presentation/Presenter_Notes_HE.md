# הכנה להצגת פרויקט Damka

משך: 15 דקות — 10 דקות לשקפים, 3 דקות להדגמה נפרדת, 2 דקות לשאלות.

השקפים באנגלית. הערות אלו בעברית, והן משולבות גם בהערות הדובר של PowerPoint.

## שקף 1: פתיחה — 20 שניות

להציג את שמות המגישים ואת שם הפרויקט. בנינו משחק דמקה ב־Java וב־JavaFX, הכולל משחק בין שני מחשבים באמצעות שרת TCP, יריב ממוחשב ופרופילים עם היסטוריית משחקים. בהצגה נתמקד בדרך שבה הרכיבים עובדים יחד. ההדגמה תבוצע בנפרד מהשקפים.

## שקף 2: המטרה והיכולות — 35 שניות

המטרה היא לאפשר למשתמש לבחור בין משחק מול אדם אחר לבין אימון מול BOT, ולקבל חוויית משחק ברורה עם תוצאה שנשמרת בחשבון. במשחק ברשת צריך ששני המשתתפים יראו את אותו לוח ושלא יוכלו לבצע מהלכים מחוץ לתור. חשבונות והיסטוריה מאפשרים לשמור הישגים בין הפעלות. המשחק המקומי מול BOT זמין גם ללא שרת, אך אימון לא מקוון אינו נשמר. כללי הדמקה עצמם מרוכזים ב־Game ומשמשים בשני המצבים. להזכיר בקצרה: תנועה אלכסונית, אכילה מחייבת והכתרה; אין צורך ללמד כאן את כל המשחק.

## שקף 3: טכנולוגיות וכלי פיתוח — 40 שניות

שפת המימוש היא Java, עם יעד תאימות לגרסה 17. JavaFX משמשת לבניית מסכי ההתחברות, המשחק והפרופיל; CSS מגדיר את העיצוב והאנימציות ממומשות ברכיבי JavaFX. התקשורת משתמשת ב־Socket וב־ServerSocket מתוך java.net, עם הודעות טקסט ב־UTF-8 שמסתיימות בסוף שורה. הנתונים נשמרים ב־SQLite, שאליו השרת ניגש באמצעות JDBC.

JDBC הוא קיצור של Java Database Connectivity. זהו המנגנון שבו קוד Java עובד מול מסד הנתונים. בפרויקט, ProfileDatabase משתמשת בו כדי לפתוח חיבור ל־SQLite, לשלוח שאילתות SQL ולקרוא או לשמור נתונים. למשל, כשנשמר חשבון חדש, הקוד שולח את פעולת ההוספה דרך JDBC אל קובץ מסד הנתונים. זהו חיבור למסד הנתונים, בנפרד מחיבור ה־TCP שבין יישום השחקן לשרת.

כלי הבנייה הוא Gradle, והבדיקות נכתבו באמצעות JUnit 5. Git ו־GitHub שימשו לניהול גרסאות. גרסאות שמופיעות בקובצי הפרויקט: JavaFX 17.0.6, Gradle 8.8, sqlite-jdbc 3.50.3.0 ו־JUnit 5.10.2. אין צורך להקריא את כל המספרים; העיקר הוא להסביר את התפקיד של כל טכנולוגיה.

## שקף 4: מבנה המערכת ובחירת TCP — 55 שניות

להצביע על שני הלקוחות ועל השרת. כל לקוח מחובר לשרת; אין חיבור ישיר בין שני השחקנים. השרת מנהל חדרים, ובכל חדר נמצא אובייקט Game שמחזיק את מצב המשחק המקוון. כך יש מקור מוסמך אחד שמאמת מהלכים ומעדכן את שני המשתתפים. מסד SQLite נמצא בצד השרת ושומר חשבונות ותוצאות.

אפשר היה לבחור HTTP עם בקשות חוזרות לקבלת עדכונים. בחרנו TCP מתמשך כדי להעביר בקשות ועדכונים לשני הכיוונים דרך אותו חיבור. זו בחירה שמתאימה לפרויקט, ולא טענה ש־TCP תמיד עדיף. גם HTTP פועל בדרך כלל מעל TCP; כאן ההשוואה היא בין פרוטוקול ההודעות שלנו על Socket לבין תכנון מבוסס בקשות HTTP.

חיבור TCP נפתח כבר בהרשמה או בהתחברות. לאחר ההזדהות אותו Socket משמש לחדרים, למהלכים ולפרופיל. יצירת חדר משייכת שני חיבורים למשחק אחד.
מקורות להכנה: https://docs.oracle.com/javase/tutorial/networking/sockets/ ; https://www.sqlite.org/about.html

## שקף 5: מבנה המחלקות והקשרים — 65 שניות

זהו תרשים של המחלקות המרכזיות ושל קשרי שימוש וקריאה, ולא תרשים מלא של כל המשתנים והירושות. מתחילים ב־DamkaFX שמרכזת את התנהגות הממשק. AccountView, BoardView ו־ProfileWindow מציגות את המסכים; אירועים חוזרים ל־DamkaFX באמצעות callbacks. ServerConnection מנהלת את חיבור ה־TCP, קריאת ההודעות וכתיבה לפי סדר.

בשרת, DamkaServer מקבלת חיבורים ומנתבת בקשות מתוך handleClient. Room אחראית לחדר, לשני המשתתפים ולשידור מצב המשחק. handleMove מזהה את ההקשר ואת התור, ואז מעבירה את בדיקת חוקי הדמקה ל־Game.move. Game מחזיקה Board ונתוני שחקנים וכלים ומספקת גם getValidMoves ובדיקת מנצח. ProfileDatabase מטפלת בהרשמה, בהתחברות ובשמירת תוצאות; גם DamkaServer פונה אליה ישירות, למשל בזמן התחברות ובקשת פרופיל, ו־Room שומרת בה את תוצאת המשחק.

במשחק המקומי DamkaFX מחזיקה Game משלה ומשתמשת ב־BotPlayer.findBestMove. החיפוש פועל על עותקים של Game. חשוב להדגיש: המחלקה Game משותפת כמימוש של הכללים, אבל אין אובייקט משחק יחיד שמשותף לכל המצבים. לכל חדר יש משחק נפרד; ל־BOT המקומי משחק נפרד; ובחיפוש נוצרים עותקים זמניים.

## שקף 6: מהלך אחד מקצה לקצה — 75 שניות

להתחיל מלחיצה על כלי וממשבצת היעד. DamkaFX שולחת דרך ServerConnection הודעת MOVE עם שורת ועמודת מקור ויעד. המספרים בדוגמה הם קואורדינטות שמתחילות באפס. השרת מזהה את השחקן לפי ה־Socket המאומת; Room בודקת את ההקשר ואת התור, ו־Game.move בודקת את חוקי הדמקה. בקשה לא חוקית מקבלת ERROR בלי לשנות את הלוח.

כאשר המהלך מאושר, שני הלקוחות מקבלים בסדר זה MOVE_APPLIED, BOARD ו־TURN. הראשונה מאפשרת להנפיש את המהלך, השנייה מכילה תמונת לוח של 64 סימנים, והשלישית מציינת את התור. הלקוח משהה את הטיפול בהודעות המאוחרות בזמן האנימציה, ואז מציג את המצב המעודכן.

TCP מעבירה זרם בתים ואינה מסמנת לבדה גבולות הודעה. בחרנו שורת טקסט לכל הודעה: println כותבת סוף שורה ו־readLine קוראת עד סוף שורה. הנקודה מייצגת תא ריק, x/o כלי רגיל ו־X/O מלך.

הרשת נקראת בחוט רקע; כתיבה נעשית דרך עובד כתיבה יחיד ששומר סדר. Platform.runLater מעבירה עדכוני מסך לחוט JavaFX. חיפוש BOT במימוש הנוכחי מתבצע מחוט הממשק.
לקראת שאלה: הלקוח בוחר ומציג; הסמכות לאשר מהלך מקוון נמצאת בשרת.

## שקף 7: כללי המשחק ובחירת מהלך BOT — 60 שניות

הכללים מרוכזים ב־Game, ולכן השרת והמשחק מול BOT נשענים על אותו מנגנון של תנועה, אכילה, רצף אכילות והכתרה. BotPlayer מחפשת מהלך באמצעות Minimax עם גיזום Alpha-Beta. כל אפשרות נבדקת על עותק עצמאי של Game, כדי לא לשנות את המשחק הפעיל בזמן החיפוש.

להסביר את המספרים מלמטה למעלה. כל ציון הוא מנקודת המבט של ה־BOT. במהלך A, היריב יכול לבחור בין ציון 3 לבין מינוס 3, ולכן MIN מחזירה מינוס 3. במהלך B, היריב יכול לבחור בין 0 לבין 3, ולכן MIN מחזירה 0. בשורש, ה־BOT משווה MAX בין מינוס 3 לבין 0 ובוחר במהלך B. התוצאה המספרית היא 0, והמהלך שנבחר הוא B, המסומן בירוק. 0 הוא ציון הערכה של מצב הלוח בעומק שנבדק; הוא אינו הודעה שהמשחק הסתיים בתיקו. הציונים בשקף הם המחשה קצרה, לא עקבה של משחק מסוים.

ההערכה מבוססת על ערך כלי BOT פחות ערך כלי היריב: כלי רגיל 3, מלך 6. ניצחון או הפסד מקבלים ציון מכריע. רמות הקושי בוחרות עומק 1, 2 או 3; העומק נספר לפי צעד או קפיצה בודדת. ברצף אכילות אותו שחקן יכול להמשיך, ולכן החיפוש בודק מי השחקן הנוכחי ולא מחליף צד אוטומטית.

Alpha-Beta מצמצמת ענפים שאינם יכולים לשפר את הבחירה בתוך החיפוש. אין צורך להיכנס להוכחה או להציג סיבוכיות בשקף.

## שקף 8: חשבונות ושמירת תוצאות — 45 שניות

השרת מטפל בהרשמה ובהתחברות ושומר את הנתונים בשתי טבלאות SQLite. profiles כוללת שם משתמש, תאריך יצירה, salt וגיבוב סיסמה; הסיסמה עצמה אינה נשמרת. בהתחברות מחשבים שוב גיבוב עם ה־salt השמור ומשווים אותו לערך שבמסד. המימוש משתמש ב־PBKDF2-HMAC-SHA256.

game_results כוללת את פרטי המשחק ואת תוצאתו. אין טבלה נפרדת של מוני ניצחונות: הסטטיסטיקה מחושבת מתוצאות המשחקים. מזהה משחק ייחודי מונע שמירת אותה תוצאה פעמיים. בתצוגה יש הפרדה בין משחקים מקוונים למשחקי BOT, וההיסטוריה מציגה את 100 התוצאות האחרונות.

תוצאה מקוונת נקבעת בשרת. תוצאת BOT מדווחת מהלקוח ונשלחת רק אם אותו חשבון ואותו חיבור נשארו פעילים מתחילת המשחק ועד סופו. גיבוב סיסמה במסד אינו מצפין את התקשורת ברשת.

## שקף 9: בדיקות ואימות המערכת — 40 שניות

הבדיקות מחולקות לשלוש שכבות: כללי המשחק, התקשורת ושמירת הנתונים. לתת שתי דוגמאות מוחשיות: מהלך מחוץ לתור נדחה והלוח נשאר ללא שינוי; שמירה חוזרת של מזהה תוצאה אינה מכפילה את הסטטיסטיקה. בדיקות TCP משתמשות בחיבורים אמיתיים ל־loopback, ובדיקות SQLite במסדים זמניים.

בנוסף בוצעו הרצות ידניות עם שני חלונות לקוח. במהלך העבודה נבדקו הודעות שגיאה ואנימציות, ודווחו בעיות בתצוגת הודעה אחרי מהלך תקין ובמיקום האנימציה לאחר שינויי גודל. המספר 48 מבוסס על ההרצה המתועדת מ־12 באוקטובר 2026; אין להציג אותו כמדידה חדשה של היום.

## שקף 10: אתגרים ופתרונות — 50 שניות

האתגרים תואמים לפרק 12.2 בספר הפרויקט. תחילה נדרש ללמוד את כללי הדמקה: תנועה, אכילה מחייבת, רצף אכילות והכתרה, ולהגדיר מצבי משחק לבדיקת המימוש. JavaFX הייתה ספריית ממשק חדשה, ולכן היה צורך ללמוד איך לארגן רכיבים בחלון ואיך לחבר כפתורים ולחיצות על הלוח לפעולות.

ב־TCP יושם לראשונה בפועל הידע התאורטי מקורס רשתות תקשורת, באמצעות חיבורים בין לקוחות לשרת והעברת הודעות משחק. בנוסף, המעבר מהניסיון המוכר בממשקי HTML ל־JavaFX דרש ללמוד דרך שונה לארגון הממשק ולטיפול באירועי המשתמש.

## שקף 11: התרומה שלנו והשימוש ב־AI — 55 שניות

השקף מציג את תחומי האחריות שהוגדרו בפרויקט, בהתאם לפרק 11 בספר. תחום האחריות של רביע הוא לוגיקת המשחק: תנועה ואכילה, ניהול תורות והכתרה, וקביעת סיום המשחק והמנצח. תחום האחריות של מותנא הוא חיבור TCP בין לקוחות JavaFX לשרת: פתיחת חיבורים והעברת בקשות ותשובות לשמירת מצב משחק מסונכרן.

בהתאם לפרק 10, נעשה שימוש נרחב ב־Codex וב־GitHub Copilot ללמידה ולתכנון, לכתיבת הקוד ולשינויו, לעיצוב הממשק ולהכנת בדיקות ותיעוד. תהליך העבודה כלל הגדרת דרישות, קבלת הצעות, קריאת הקוד וההסברים, הרצה ובדיקות והתאמות בהתאם לתוצאות. תחומי האחריות מתארים את חלוקת הנושאים; הם אינם טענה שכל הקוד בתחום נכתב באופן עצמאי ללא סיוע.

## שקף 12: סיכום ומסקנות — 45 שניות

לסכם בתוצר: שני לקוחות מסונכרנים, שרת שמאמת מהלכים, מנוע כללים משותף ונתונים שנשמרים בפרופיל. הלמידה המרכזית היא חיבור ידע תאורטי ברשתות לתקשורת מעשית, עבודה עם JavaFX והפרדת כללי משחק מהתצוגה.

קישור המאגר מופיע בשקף וניתן ללחיצה. השקף מסכם את התוצר ואת הידע שנרכש; תחומי האחריות ותהליך העבודה עם AI הוצגו בשקף נפרד.

כיוון פיתוח עתידי הוא צ׳אט בתוך החדר, דרך חיבורי TCP הקיימים והשרת. זו הצעה להמשך ולא יכולת קיימת.

תקציב המצגת הוא 10 דקות לשקפים, 3 דקות להדגמה נפרדת ועוד 2 דקות לשאלות. לתרגל מראש תשובות: למה יש שרת? מתי נפתח Socket? מי מאשר מהלך? איך BOT בוחרת? איך נמנעת שמירה כפולה? מה ההבדל בין גיבוב סיסמה להצפנת התקשורת?

## שקף 13: תודה ושאלות — 15 שניות

להודות למנחה ולקהל ולהזמין שאלות. אפשר להשאיר את השקף מוצג בזמן הדיון. ההדגמה מוכנה בנפרד ואינה שקף במצגת.

## חזרה לפני ההצגה והדגמה נפרדת

- להפעיל שרת ושני לקוחות ולבדוק כניסה לפני תחילת ההצגה.
- לתרגל פעם אחת עם שעון, כולל המעבר בין המצגת ליישום.
- להכין שני חשבונות בדיקה ולא להציג סיסמאות אישיות.
- להדפיס את קובץ Handout אם נדרש עותק למשתתפים.
